# 管理员二层网络诊断接口建议

2026-09-15，用户希望把 VLAN 排障过程变成对管理员配置二层网络有帮助的接口。本文件是基于当前源码和本次对照探测的建议，尚未成为已接受的产品合同，也未实现新 RPC。实际结果见[本次诊断](README.md)；原 LB Goal 状态仍以[执行状态](../../../status.md)为准。

## 入口与使用场景

在 `PlatformNetworkService` 增加一组管理员诊断 RPC：

| 建议 RPC | 行为 |
|---|---|
| `CreateLayer2Diagnostic` | 提交确定节点、接口、预期标签方式和允许目标的诊断，返回 `diagnostic_id`；主动探测异步执行 |
| `GetLayer2Diagnostic` | 纯查询诊断状态、逐节点事实、证据及建议，不因刷新而再次发包 |

初期可在“配置 VLAN 网络/地址池”流程中提供“检查二层连接”，也可诊断已受 kc/OVS 管理的接口。接口是否可接管与它是否能够收发二层流量分别判断：ens35 已在 OVS 中，并不意味着管理员不能查看其连通性。

当前已有 [`ListNodeInterfaces`](../../../../../api/network/v1/egress.proto)、[`NodeFactsCollector`](../../../../../internal/data/node_facts_collector.go) 和[节点事实读取](../../../../../internal/data/kc_node_facts.go)。它们提供接口身份、IP、master、OVS/kc 占用、默认路由和时效等事实，未实现主动 ARP、跨节点验证或 vSphere 配置读取。因此应复用已有事实基础，并新增显式诊断动作。

## 输入要区分两种 VLAN 含义

建议输入包括 cluster ID、明确的 Node UID 集合、接口名及事实 fingerprint、预期封装 `tagged`/`untagged`、主机实际发送的 VLAN ID、网关地址、可选且已登记的对照目标，以及是否启用同源的标签方式对照。

**上游逻辑 VLAN 102 与主机发送标签 102 不是同一个事实。** 管理员可以声明上游网络为 VLAN 102，同时虚拟机侧使用 untagged；诊断应分别展示两个值，并标记哪个来自管理员声明、哪个来自实际观测。当前 kc `VlanNetwork.vlanID` 的合同保持，不能在这项建议中重新解释既有字段。

首版目标限于指定网关和已登记的对照端，禁止任意地址段扫描、任意命令、任意 shell 或把 SSH 密码/密钥塞进请求。`diagnostic_id` 固定输入及幂等键，查询不会启动另一轮实验。

## 返回可操作的证据

每个节点独立返回：

- 身份与时点：Node UID、接口 MAC/ifindex、当前 master、地址/路由、事实时间、预期封装及实际发送封装。节点替换或接口身份漂移使该次结果失效。
- 发包与收包：源地址的使用方式、目标、尝试次数、发送系统调用结果、NIC 计数增量、收到的 ARP sender MAC/IP、目标匹配、帧或 offload 辅助信息中的 VLAN 标签。单凭发送计数不宣称上联已收到。
- 对照结果：相同节点、源地址和目标下，只改变 tagged/untagged 一项；普通源地址与 `0.0.0.0` 分开记录。对网关和正常虚拟机的结果分别展示。
- 结论：`pass` / `fail` / `not_verified` 及精确检查对象。无回复只能证明“本次没有观察到匹配回复”，不能自动推断网关坏、整个 VLAN 不通或交换机配置错误。
- 管理员提示：已成立的事实、由它支持的可能原因、还缺什么信息，以及定位页面时需要的 MAC/端口组/上联信息。

例如，本次可以形成“相同普通源地址下，untagged 收到网关及对照虚拟机回复，tagged 102 未收到；当前接口支持的有效接入方式与期望不符”的提示，并要求核对虚拟机端口组的标签处理。若没有 vSphere 连接器，端口组类型和上联仍显示 `not_verified`；不能从 Linux 网卡名称推断 ESXi 配置已经查明。

不要让一个总 `ready=true` 隐去单节点失败。也不要把 ARP 通过直接转成 Public 池 verification、开放分配、LB 健康或互联网已通。

## 执行与权限

采用两档能力：基础事实检查复用现有只读采集；主动 ARP 由另行启用的受限节点执行器承担。现有采集器已丢弃 Linux capabilities，不能声称它目前能够发原始以太帧，也不能为了这项能力直接把所有现有采集器改成 privileged。

主动执行器只在确实需要的情况下取得 `NET_RAW`，不授予 `NET_ADMIN`，不提供 IP、route、OVS、VLAN 接口或虚拟交换机配置修改功能。服务端固定命令/报文结构，绑定已核验的 Node UID、接口身份和诊断 ID；为每个接口设并发上限、短超时、包数上限及审计记录。默认不周期重跑。

普通 ARP 源地址必须来自已验证的本接口地址或本次诊断已保留的实验地址；不得自动挑选一个“看起来没人用”的地址。DAD 无回应不能证明地址已获分配。没有适用普通源地址时可做明确标记的零源地址检查，但零源地址无回复不能阻止管理员查看其他正向证据。

Network 拥有诊断受理、有限执行、超时和报告，复用现有持久任务的执行机制；不把诊断重试混入 VPC/LB reconciliation。平台授权来自可信上下文，禁止任意 header/body 声明管理员。此次受控入口不证明 IAM 集成已完成。

首版不接管 vCenter/物理交换机配置，也不需要保存它们的凭据。未来如添加只读平台连接器，可补充真实端口组、标签规则、vmnic 和上联映射，仍区分来源与采集时间。

## 实施前的验收范围

必要用例应来自这次实际问题：普通虚拟机通而主机 tagged 不通；同源的 tagged/untagged 对照；网关忽略零源地址而回复普通源地址；VLAN offload 下的标签读取；接口被 OVS 管理；节点/接口身份替换；探测超时、权限不足和单节点缺失；管理员越权和超额发包拒绝；GET 不发包；诊断不改网络、不自动开放池。

这是一项独立的管理员能力，不能用它替代 NET-U09 的业务数据面验收。用户后续已明确将原实验改为 untagged，实际执行见下节；该调整不等于授权或完成本接口的实施。

## 后续实测补充：目标可用性与清理差异

参见[ani-01 untagged IP 实测](untagged-followup.md)。正常对照 VM 在首次检查可达，随后从本机 SSH 与节点 ARP 均无回应；网关仍可往返，用户随后确认 VM 已关机。接口应记录对照目标身份、检查时点和独立可用性，目标变化时将相关推断置为未知，避免把它归因于 VLAN。

未来若单独开放需要配置的诊断，必须将地址、路由、OVS 状态的清理结果与完整内核状态差异分开报告；不能只有一个概括性 restored 布尔值。当前建议的首版仍只发送受限报文，不因此自动获得配置主机接口的权限。
